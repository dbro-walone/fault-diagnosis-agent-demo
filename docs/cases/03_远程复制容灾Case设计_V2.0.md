# Case 03：远程复制容灾诊断设计 V2.0

> Case ID：`remote_replication_lag_001`  
> 数据实现：`cases/remote_replication_lag_001/`，Case V1.0 Mock 数据包，已通过统一校验器。

## 1. 场景

生产存储 Storage-A 将 LUN-PROD 远程复制到容灾存储 Storage-B。复制网络出现丢包/拥塞，复制带宽下降、待复制数据积压、RPO 增大；本地前端业务暂未明显受影响。诊断需要区分源端后端压力、复制端口/网络、远端写入瓶颈和复制会话配置等故障域。

## 2. 整体流程

```mermaid
flowchart LR
    A["远程复制RPO超标/会话降级"] --> B["定位复制会话及源端/目标端"]
    B --> C["分解本地业务、源端、链路、远端四个故障域"]
    C --> D["查询复制积压、带宽、丢包和远端写入"]
    D --> E["锁定复制链路拥塞"]
    E --> F["检查源端负载、远端池和配置竞争候选"]
    F --> G["确认链路拥塞导致复制滞后"]
```

## 3. 拓扑

```mermaid
flowchart LR
    APP["生产业务"] --> LUN1["Storage-A / LUN-PROD"]
    LUN1 --> RS["Replication Session"]
    RS --> LINK["Replication Network"]
    LINK --> LUN2["Storage-B / LUN-DR"]
```

源端和目标端必须是两个独立设备边界，复制会话和链路位于两者之间。

## 4. 候选

1. 源端 Storage-A 后端性能瓶颈；
2. 源端复制端口异常；
3. 复制网络拥塞/丢包；
4. 目标端 Storage-B 写入或存储池瓶颈；
5. 复制会话暂停、限速或配置异常。

## 5. Round 0：输入与现象

输入可以是：

- “远程复制 RPO 从 30 秒升到 12 分钟”；或
- 复制会话告警“同步滞后/会话降级”。

标准化对象：ReplicationSession-RS01；时间窗：16:00～16:15；现象：复制积压与 RPO 超标。

## 6. Round 1：资源映射与基线

- `business_mapping/topology_query` 定位源 LUN、复制会话、复制端口、网络、远端端口和目标 LUN；
- `kpi_query` 确认 RPO 30s→720s、积压 0.8GB→96GB、复制吞吐 2.4GB/s→0.35GB/s；
- 本地 LUN前端时延仍在 2.1～2.5ms，说明当前主要影响为容灾目标而非本地业务。

## 7. Round 2：四域并行取证

- 源端：后端时延、池利用率、复制发送队列；
- 链路：端口错误、丢包、重传、带宽和网络告警；
- 远端：接收队列、目标池写入时延和容量；
- 会话：运行状态、暂停/限速配置和同步模式。

## 8. Round 3：强证据与重规划

建议 Mock 数据：

| 指标 | 基线 | 异常值 |
|---|---:|---:|
| 复制吞吐 | 2.4GB/s | 0.35GB/s |
| 网络丢包率 | 0.01% | 4.8% |
| TCP/协议重传 | 20/s | 3,200/s |
| 待复制数据 | 0.8GB | 96GB |
| RPO | 30s | 720s |
| 源端池时延 | 2.6ms | 2.9ms |
| 远端池写时延 | 3.1ms | 3.4ms |

链路丢包与吞吐下降、积压增长严格同窗，网络候选成为领先。Planner 将源端/远端深度分析降级，优先查询复制端口日志、链路告警和恢复段。

## 9. Round 4：竞争候选

- 源端池和后端磁盘无相应压力；
- 远端池容量、写入时延与接收队列正常；
- 会话未暂停、未限速、配置未变化；
- 复制端口物理 Up，但链路层丢包/重传显著，说明“端口在线”不能排除网络质量问题；
- 若网络恢复后吞吐回升、积压下降、RPO收敛，形成恢复闭环。

## 10. Round 5：结论

```text
复制网络丢包/拥塞
→ 重传增多、有效吞吐下降
→ ReplicationSession待复制数据积压
→ RPO持续增大并触发会话降级告警
→ 网络恢复后积压下降、RPO收敛
```

结论必须明确：当前本地生产 I/O 未明显受影响，但容灾恢复点目标失守，风险属于容灾保护能力下降。

## 11. 最小证据链

- RPO/积压异常事实；
- 复制会话与源/远端拓扑路径；
- 链路质量异常与吞吐下降；
- 时间顺序与传播一致；
- 源端、远端和配置竞争域检查；
- 可选恢复闭环。

## 12. LUI 与图谱重点

- 诊断态势区同时显示“业务影响：容灾保护降级，本地业务正常”；
- 当前行动区显示正在验证的故障域；
- KPI详情用统一时间轴叠加 RPO、积压、吞吐、丢包、源/远端时延；
- 点击复制会话同时高亮源端、链路和远端；
- 不将“端口Up”错误解释为链路健康。

## 13. 验收

- 双设备边界、复制方向和会话对象清晰；
- 先分故障域，再以证据收敛，不能从告警名称直接跳结论；
- 链路强证据与源端/远端竞争检查完整；
- 可区分本地业务影响与容灾RPO影响；
- 与另外两类 Case 共用统一 Runtime 和 View Model。

## 14. Mock 数据包覆盖

数据包包含 13 个资源、13 条拓扑关系、2 条告警、7 条原始日志、7 个日志指纹、8 组 KPI、5 个候选、9 个任务、12 条证据和 8 幕回放。

关键实现约束：

- `Storage-A → RS01 → Replication-WAN-01 → Storage-B` 方向和双设备边界明确；
- RPO、积压、复制吞吐、丢包和重传使用统一时间轴；
- 源端Pool时延、远端写时延、生产LUN时延和会话配置均提供正常值/反证；
- 复制端口保持 Up 只用于削弱物理端口故障，不能覆盖 WAN 质量异常；
- WAN恢复后积压下降、RPO收敛形成恢复闭环；
- `business_impact.level=protection_degraded` 明确影响容灾保护而非本地生产I/O。
