# 故障诊断 Agent 业务验收测试基线 V1.0

> 文档状态：评审稿  
> 日期：2026-08-01  
> 适用对象：`故障诊断Agent-demoV2` 最终可运行产品  
> 验收性质：技术栈无关、黑盒业务验收  
> 基线范围：3D 图谱与拓扑、诊断 LUI、诊断语义、三套基线 Case、回放与扩展能力

---

## 1. 文档目的

本文档用于回答一个唯一问题：

> 本地代码 Agent 交付的最终产品，是否从用户可观察行为和故障诊断业务语义上，真正实现了已经冻结的产品目标？

本文档不是开发框架测试规范，不限定 Flask、FastAPI、Java、Node.js、React、Vue、REST、SSE、数据库或部署方式。实现方可自行选择技术路线，但最终产品必须通过同一套业务验收。

业务验收只关心：

1. 图谱与拓扑是否准确、清晰地表达资源关系、故障知识和诊断路径；
2. LUI 是否在诊断全过程持续说明 Agent 知道什么、正在做什么、为什么这样做；
3. Fact、Evidence、Candidate 与 Conclusion 是否按照冻结语义逐步形成；
4. 三套 Case 是否按各自业务机理完成诊断，而不是播放固定动画；
5. 新增 Case、替换对象和缺失证据后，产品是否仍能按统一机制运行；
6. 用户是否能够理解、探索、追溯和复核诊断结论。

## 2. 验收边界

### 2.1 本基线验收什么

| 验收对象 | 业务问题 |
|---|---|
| 产品主流程 | 用户能否从模型探索进入诊断，并完成诊断与回放 |
| 3D 双平面 | 是否同时表达实例拓扑、故障知识图谱及跨层映射 |
| 三种主视图 | 融合诊断、全量拓扑、全量故障图谱是否各自可用且状态连续 |
| 图谱交互 | 聚合、钻取、路径、聚焦、语义缩放与用户浏览保护是否符合预期 |
| 五层 LUI | 是否持续展示会话、态势、当前行动、候选与调查工作区 |
| 三级事实 | 是否支持行动摘要→证据预览→原始事实详情的完整追溯 |
| 诊断语义 | Fact→Evidence→Candidate→Conclusion 是否边界清晰且可审计 |
| 三套 Case | Controller 热复位、共享存储扰邻、远程复制滞后是否语义正确 |
| 历史回放 | 是否只呈现当时已经产生的信息，且可返回实时上下文 |
| 场景扩展 | 未知第四 Case 是否能复用现有产品能力完成展示与诊断 |

### 2.2 本基线不验收什么

以下内容由实现方自行建立工程测试，不作为本业务验收的框架性门槛：

- 使用哪一种编程语言、前后端框架或状态管理库；
- 内部接口采用何种通信协议；
- 内部目录结构、类名、函数名和代码覆盖率；
- 使用何种数据库、消息系统或日志框架；
- Mock Planner 是否由规则、工作流或代码实现；
- 单元测试、静态扫描和依赖治理的具体工具。

但若上述实现选择导致用户可观察行为不符合本文档，仍按业务验收失败处理。

### 2.3 当前不纳入 V1.0 的业务范围

- 自动修复执行、审批、回滚和修复结果验证；
- 真实 DME、ES、CMDB、告警或性能接口接入；
- 大模型私有思维链展示；
- 生产级概率或置信度模型；
- Case V2 新数据规范；
- 大规模生产拓扑的容量极限测试。

| 优先级 | 依据 | 验收作用 |
|---:|---|---|
| 1 | Diagnosis Runtime、可执行本体与推理语义基线 | Fact、Evidence、Candidate、Conclusion 与会话状态 |

若视觉方案、工程实现与业务语义发生冲突，以业务语义正确和可追溯为先；若 Case 数据真值与演示文案冲突，以当前归档数据包及其设计文档为准。

## 4. 验收原则

### 4.1 黑盒原则

验收人员通过自然语言输入、场景选择、界面交互、诊断过程、回放结果和产品导出物判断结果。除扩展性与反硬编码测试外，不要求验收人员阅读实现代码。

### 4.2 可观察原则

每个关键业务判断必须在产品中具有可观察证据。不能以“内部已经计算”“日志里应该存在”代替产品表达。

### 4.3 过程优先原则

诊断结论正确但过程错误，仍视为验收失败。例如：提前展示根因、跳过竞争候选、用固定分数播放结论、把数据缺失解释为正常。

### 4.4 语义一致原则

同一会话中，主画布、LUI、时间线、候选列表、证据详情和结论必须来自同一诊断时点。不得出现主画布处于 Round 2、右侧已经显示 Round 5 结论的状态撕裂。

### 4.5 不可平均抵消原则

本基线采用硬门槛。关键语义失败不能被视觉评分、用例总通过率或非关键功能的高分抵消。

### 4.6 数据驱动原则

三个 Case 应共用相同的产品结构、诊断语义、LUI 和交互机制。场景差异通过资源、关系、事实、证据模板和场景配置表达，不通过复制页面或按 Case ID 编写业务分支表达。

## 5. 测试等级、结果与证据

### 5.1 严重级别

| 等级 | 定义 | 验收处理 |
|---|---|---|
| P0 Blocker | 破坏核心产品目标、诊断真实性或三套 Case 主线 | 任一失败即不通过 |
| P1 Critical | 严重影响理解、追溯、关键交互或扩展能力 | 必须 100% 通过 |
| P2 Major | 影响局部体验或非关键业务表达 | 允许修复后复测，不得遗留影响演示的问题 |
| P3 Minor | 文案、轻微视觉或低频体验问题 | 可记录为已知问题，不影响核心准入 |

### 5.2 测试结果

```text
NOT_RUN | PASS | FAIL | BLOCKED | NOT_APPLICABLE
```

- `PASS`：结果、禁止项和证据要求全部满足；
- `FAIL`：任一预期不满足或出现禁止行为；
- `BLOCKED`：前置条件不成立，不能视为通过；
- `NOT_APPLICABLE`：只允许用于明确不适用的非 P0/P1 用例，并需评审人批准。

### 5.3 每条用例的最小证据

每条用例至少保留一种主证据和一种辅助证据：

| 证据类型 | 适用内容 |
|---|---|
| 截图 | 静态布局、状态、标签、候选、证据详情和最终结论 |
| 操作录像 | 聚合钻取、视图切换、相机保护、状态流转和回放 |
| 会话导出 | 当前时点的事实、证据、候选、计划和结论摘要 |
| 测试记录 | 输入、操作步骤、时间、结果、缺陷与复测结论 |
| 评审记录 | 可读性、路径识别、视觉层级和主观体验评分 |
| 扩展变更说明 | 第四 Case 加入方式及对既有产品模块的影响范围 |

P0 用例必须保留录像或连续截图，以及能够证明诊断时点的会话导出/测试记录。

## 6. 验收数据与执行前提

### 6.1 三套权威 Case

| Case ID | 场景 | 核心业务挑战 |
|---|---|---|
| `controller_warm_reset_001` | Controller-0A 热复位 | 触发机制→复位→接管→业务影响 |
| `noisy_neighbor_io_contention_001` | 共享存储扰邻 | 从受害者 B 定位共享瓶颈，再反向发现施压者 A |
| `remote_replication_lag_001` | 远程复制滞后 | 区分源端、链路、远端和配置四个故障域 |

### 6.2 扩展性验收 Case

验收团队在开发完成后提供一套实现方此前未针对性适配的 `case_extension_x`：

- 使用现有对象类型、关系类型、Fact 类型和诊断动作；
- 包含新的对象 ID、名称、时间窗和 KPI 数值；
- 至少 3 个候选、1 条最小证据链和 1 个竞争候选；
- 至少包含拓扑、KPI、日志或告警中的三类事实；
- 含一个证据缺失变体和一个对象规模变体；
- 不要求引入新的自动修复语义。

该 Case 的具体故障内容在正式验收前不向实现方冻结，以检验真实扩展能力。

### 6.3 显示与体验基线

业务验收至少覆盖：

- 1920×1080 桌面显示；
- 1440×900 桌面显示；
- 默认浏览器缩放 100%；
- 融合首屏 30～40 个可见有效节点，目标约 36；
- 常态深钻不超过 60 个可见节点；
- 80 个节点只用于安全上限与降级验证，不作为常态界面。

这不是对具体浏览器或前端框架的限定，而是对最终业务界面的可用空间基线。

## 7. 标准用例模板

正式执行记录应使用以下结构：

```yaml
test_id: BA-NN-006
title: 共享消费者展开前不得显示 Host-A
severity: P0
case_id: noisy_neighbor_io_contention_001
requirement_refs:
  - CASE-NN-R3
  - UI-AGENT-FOCUS

preconditions:
  - 会话已完成 Round 2
  - 已发现 Controller-0A/Pool-01 共享压力

steps:
  - 检查拓扑、候选列表、当前行动和历史事件
  - 继续执行共享消费者展开动作

expected:
  - 展开前只显示受害者 B、B 路径和共享资源压力候选
  - 重规划理由说明需要展开共享资源的其他消费者
  - 展开后才出现 LUN-A/Host-A 及相应候选

forbidden:
  - Round 0～2 出现 Host-A 根因、最终结论或未来证据
  - 根据 Case 名称直接显示 Host-A

evidence:
  - Round 2 截图
  - Round 3 操作录像
  - 两个时点的会话记录
```

## 9. A 类：产品目标与主流程（5 条）

| ID | 前置与操作 | 预期用户可观察结果 | 禁止行为 | 级别 |
|---|---|---|---|---|
| BA-GOAL-001 | 打开产品，不启动诊断 | 默认进入可探索的模型视图；可查看实例、知识和关系；不自动生成候选 | 首页直接播放某个 Case 或提前显示根因 | P0 |
| BA-GOAL-002 | 在探索态输入可唯一匹配的故障现象 | 现象被标准化，显示对象/时间窗；创建对应诊断会话 | 未说明标准化结果即直接跳到结论 | P0 |
| BA-GOAL-003 | 输入对象或时间窗不足的现象 | 产品明确指出缺口并追问；补充后再开始诊断 | 模糊“业务变慢”默认路由到 Controller Case | P0 |
| BA-GOAL-004 | 完整执行任一基线 Case | 经候选、取证、证据、更新与竞争检查后到达明确终态 | 只有开场和结论，中间为不可解释动画 | P0 |
| BA-GOAL-005 | 诊断完成后返回模型探索 | 保留可识别的历史诊断摘要，但当前模型状态与历史结论清楚分离 | 历史根因永久覆盖当前资源运行状态 | P1 |

| BA-GRAPH-004 | 切换融合、全量拓扑、全量图谱 | 三种一级视图均独立可用，职责清楚 | 仅改变标题，主体内容与交互没有区别 | P0 |
| BA-GRAPH-005 | 在融合视图选中对象后切换视图 | 尽量保留同一实体选择、时间位置、展开语义层级和关键路径 | 每次切换均回到默认视口并丢失上下文 | P1 |
| BA-GRAPH-006 | 检查跨层映射 | 实例→类型→故障模式/证据的映射方向与端点准确，可查看映射含义 | 映射线只做装饰或连到错误类型 | P0 |

## 11. C 类：LUI 与三级事实（18 条）

| ID | 前置与操作 | 预期用户可观察结果 | 禁止行为 | 级别 |
|---|---|---|---|---|

| BA-UX-002 | 在结论页寻找“根因如何影响业务” | 至少 2/3 评审者在 30 秒内沿图或 LUI 说出完整根因链与影响链 | P1 |
| BA-UX-003 | 从一个 Evidence 找到原始 KPI/日志/告警 | 至少 2/3 评审者在 3 次主要交互内到达对应 Fact Detail | P1 |
| BA-UX-004 | 自由探索并返回 Agent 当前视角 | 至少 2/3 评审者无需说明即可完成，且诊断上下文未丢失 | P2 |

## 19. LUI 状态流转验收矩阵

该矩阵是 BA-LUI、三 Case 与回放用例的共同判定依据。

| 诊断阶段 | 必须可见 | 允许动作 | 禁止出现 |
|---|---|---|---|
| 模型探索 | 模型概览、对象/关系、诊断入口 | 浏览、搜索、选对象、输入现象 | 本次会话候选、未来证据、最终根因 |
| 现象标准化 | 原始输入、标准化对象、现象、时间窗、缺口 | 确认、补充信息、取消 | 未执行查询产生的 Fact |
| 范围定位 | 业务到资源映射、影响范围、当前定位理由 | 展开路径、查看对象 | 最终根因和最终支持分 |
| 候选生成 | 3～5 个候选、初始支持分、证据缺口 | 选候选查看关联知识 | 把 `LEADING` 写成根因 |
| Agent 取证 | 目标、动作、对象、时间、原因、期望证据 | 暂停、查看对象/任务 | 只显示“分析中”而无行动语义 |
| Fact 产生 | 原始值、来源、覆盖、质量 | 打开详情、关联对象 | 前端自行把 Fact 判断为结论 |
| Evidence 形成 | 作用方向、解释、Fact 引用、候选引用 | 查看血缘与候选变化 | Fact 与 Evidence 合并为一层 |
| 候选更新 | 分数前后、状态、原因、证据缺口 | 排序、查看历史 | 分数显示为概率或百分比 |
| 重规划 | 原目标、变化原因、新目标、计划差异 | 查看保留/取消任务 | 无理由切换对象或查询 |
| 结论收敛 | 根因链、影响链、竞争检查、最小证据链、风险 | 回放、导出、返回探索 | 只因分数达到阈值确认 |
| 历史回放 | 当时已有的计划、Fact、Evidence、Candidate | 跳转事件、返回实时 | 后续事实、最终结论和未来对象 |

## 20. 三 Case 最小证据链门槛

| Case | 必需证据链 | 关键竞争检查 | 确认前禁止缺失 |
|---|---|---|---|
| Controller 热复位 | 直接复位事实→watchdog 机制→0A 状态变化→0B 接管→LUN/业务影响→时间一致 | FC、SAN、Pool | 机制、接管、影响任一缺失 |
| 共享存储扰邻 | B 影响→共享路径→共享压力→沿共享关系发现 A→A 负载→A/共享/B 时间一致→恢复 | B 自身、B 链路、控制器硬件、Pool 固有故障 | 共享关系、A 负载、时间一致任一缺失 |
| 远程复制滞后 | RPO/积压→复制拓扑→链路质量→吞吐下降→传播时间一致→恢复/旁证 | 源端、远端、会话配置、端口物理状态 | 双端边界、链路质量、竞争域任一缺失 |

辅助相似案例不能替代任何必需证据。支持分达到门槛但必需链不完整时，必须继续取证或输出证据不足。

## 21. 一票否决项

以下任一项出现，业务验收结论直接为 `FAIL`：

1. 三套基线 Case 任一套无法完整完成诊断主线；
2. 双平面无法清楚表达实例拓扑、故障图谱和跨层映射；
3. 设备内外边界、共享关系或远程复制方向存在事实错误；
4. LUI 无法说明 Agent 当前目标、动作、原因和期望证据；
5. Fact、Evidence、Candidate、Conclusion 语义混乱；
6. 当前历史时点出现未来 Fact、未来对象、最终分数或最终根因；
7. 最小证据链不完整时确认根因；
8. 未检查关键竞争候选便确认根因；
9. 支持分被展示为概率或百分比；
10. 扰邻 Case 在共享消费者展开前暴露 Host-A；
11. 扰邻 Case 新增或调用专用“扰邻分析 Skill”；
12. 将远程复制端口 Up 直接解释为链路健康；
13. 将远程复制影响错误描述为本地生产业务中断；
14. 用户自由浏览时 Agent 持续抢夺相机或覆盖选择；
15. 回放时主画布、LUI 和候选列表处于不同历史时点；
16. 新增第四 Case 必须复制页面或编写 Case 专用主流程；
17. 修改结论文案或最终真值即可绕过实际证据链改变运行结论；
18. 数据缺失、部分覆盖或查询失败被解释为设备正常。
