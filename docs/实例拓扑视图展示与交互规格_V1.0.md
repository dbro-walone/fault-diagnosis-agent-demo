## 1. 文档目标

本规格用于统一实例拓扑视图中资源的空间归属、展示形态、布局层次、展开策略、关系语法、诊断状态和交互行为，作为原型设计、前端实现、数据适配与验收测试的共同依据。

实例拓扑视图采用**真实 3D 分层拓扑＋按需展开＋跨层知识映射**：

> 上层 3D 空间承载实例拓扑，下层 3D 空间承载故障知识图谱；实例拓扑内部按照“业务与计算—网络与接入—控制与服务—逻辑资源—物理资源”五个空间域稳定组织，并在域内继续细分资源子层；两层通过受控 `cross_layer` 关系连接。通过聚合、逐级展开、诊断聚焦和路径高亮控制信息规模。

本规格中的“容器”是 3D 空间边界、半透明分区或聚合外壳，不等同于二维矩形框。

## 2. 适用边界

本视图主要回答以下问题：

1. 当前资源位于存储设备内部还是外部？
2. 外部业务通过什么路径访问存储？
3. 存储设备内部资源之间如何连接、运行和承载？
4. 当前故障发生在哪个对象，影响了哪些上下游资源？
5. 主备或冗余路径是否仍然有效？

实例拓扑是整体 3D 认知模型的上层主体。故障知识图谱位于下层平面，复杂推理过程由 Session Overlay 和过程面板承载；三者共享对象 ID、相机上下文和选中状态，但诊断结论只能由 Runtime Event 产生。

## 3. 页面信息架构

页面由顶部控制区、左侧模型导航区、中央 3D 融合画布、右侧详情区和底部图例/诊断过程区组成。

| 区域 | 主要内容 | 建议占比/行为 |
|---|---|---|
| 顶部控制区 | 范围切换、观察角度、时间范围、搜索 | 固定显示 |
| 左侧模型导航区 | 资源树、知识层级、类型筛选、状态筛选 | 可折叠 |
| 中央 3D 融合画布 | 上层实例拓扑、下层故障知识图谱、跨层映射及诊断 Overlay | 模型探索态占可用区域 75%～90%；诊断态不少于50% |
| 右侧详情区 | 属性、状态、知识映射、告警、性能、上下游、关联诊断 | 选中节点后展开 |
| 底部图例/过程区 | 图例；诊断启动后承载 Planner、Skill、Evidence 和 Runtime Event | 可展开/收起 |

顶部模型视角固定包含：

```text
融合全景｜实例拓扑｜故障知识图谱｜端到端业务路径
```

实例拓扑观察角度固定为：

```text
业务｜逻辑｜物理
```

切换视角或观察角度只改变关系显隐、相机预设和视觉权重，不改变基础空间布局、对象 ID 或诊断状态。

## 4. 总体空间与布局规则

### 4.1 整体 3D 空间

| 3D 区域 | 内容 | 约束 |
|---|---|---|
| 上层实例拓扑平面 | 实例资源、物理/逻辑连接、访问路径和资源容器 | 视觉权重略高；保持资源空间归属和端到端路径 |
| 下层故障知识图谱平面 | 对象类型、故障现象、故障模式、机制、证据规则和案例 | 四层稳定分布；默认聚合，按选中和诊断上下文展开 |
| 中间映射空间 | `instance_of`、`applicable_fault_mode`、`evidence_mapping`、`case_match` 等 | 只显示当前选择或诊断相关映射，禁止初始全量发光 |

双平面共享一个 `3d-force-graph` 场景、一个相机和一个拾取系统。前端不得用两套图引擎拼接，也不得用 CSS 透视伪造 3D。

### 4.2 实例拓扑空间域

| 空间域 | 资源范围 | 视觉表达 |
|---|---|---|
| 设备外部资源域 | 业务、主机、客户端、SAN/IP 网络、DNS、NTP、AD/LDAP等 | 位于设备容器外 |
| 存储集群域 | 多台存储设备组成的集群 | 低亮度虚线或浅透明外层容器 |
| 存储设备边界 | Storage Device | 青蓝色半透明根容器 |
| 设备内部资源域 | 控制器、端口、服务、逻辑资源、物理组件等 | 位于设备容器内 |
| 待确认资源域 | 无法确定归属或关系的资源 | 独立灰紫色虚线区域 |

### 4.3 布局方向

主布局固定为从左到右：

```text
业务 → 主机/客户端 → SAN/IP网络 → 边界端口
→ 控制与服务 → 逻辑资源 → 物理资源
```

不采用无约束的全局随机力导向布局。双平面高度、五个拓扑空间域、四层知识图谱和关键路径使用固定或半固定坐标；局部展开时允许在所属区域内自动避让，但不得改变资源所在的空间域和内部区域。

### 4.4 存储设备内部区域

| 内部区域 | 主要资源 | 展示原则 |
|---|---|---|
| 前端接入区 | FC端口、ETH端口、逻辑端口、接口模块 | 靠近设备左侧边界 |
| 控制与服务区 | 控制器、Block Service、NAS Service | 控制器单体优先展示 |
| 逻辑资源区 | LUN、文件系统、存储池 | 当前路径资源展开，其余聚合 |
| 物理资源区 | 磁盘、硬盘框、BBU、电源、风扇 | 默认按资源簇或类别聚合 |

四个区域使用弱背景分区或标题标识，不创建额外的实体资源节点。

### 4.5 设备边界规则

1. Storage Device 同时具有“资源实例”和“内部资源容器”双重身份。
2. 设备折叠时表现为单个设备节点；展开时表现为内部资源根容器。
3. 设备边框状态表示整机健康或受影响状态，内部节点独立表达组件状态。
4. 设备外部链路必须通过 FC、ETH 等边界端口进入设备。
5. 外部资源不得直接连接 Controller、LUN、File System 或 Storage Pool。
6. 资源归属优先使用空间包围表达，不为每个内部资源重复绘制 `contains` 连线。

| 情况 | 展示规则 |
|---|---|
| 已知资源、未知所属设备 | 放入“待确认资源”区域 |
| 已知两端资源、关系类型未知 | 使用灰紫色低透明度虚线，标记“关系待确认” |
| 资源类型未知 | 使用通用方形节点和“未知类型”标签 |

| 同一资源存在多个归属冲突 | 不由前端猜测；标记数据冲突并进入待确认区域 |

## 6. 节点与容器视觉语法

### 6.1 基础原则

1. 实例资源使用青蓝色系，基础颜色表达资源身份，不表达健康状态。
2. 健康状态、诊断状态和选中状态通过外环、光晕、描边及透明度表达。
3. 相同资源类别跨页面保持相同基础造型。
4. 聚合节点使用叠层造型、数量徽标和摘要状态表达。
5. 存储设备和集群使用容器造型，不与内部组件画成同级普通节点。

### 6.2 标签层级

| 缩放级别 | 常驻标签 |
|---|---|
| 全景 | 业务、设备、集群、资源簇名称 |
| 中景 | 控制器、服务、LUN、文件系统、存储池 |
| 近景 | 端口、模块、磁盘、对象 ID 和状态 |

节点仅展示识别所需的最少信息。完整属性、告警、性能和关系详情进入右侧面板。

### 6.3 聚合节点摘要

聚合节点至少展示：

```text
资源类型/聚合名称
总数 × N｜异常 N｜注意 N
```

异常成员存在时，聚合节点必须显示异常数量，不得仅用“部分异常”等模糊描述。

## 7. 关系与连线规则

实例拓扑的正式关系类型共七类；“待确认关系”是数据质量状态，不计入正式关系类型。

| 关系类别 | 视觉表达 | 默认常驻 | 典型语义 |
|---|---|---|---|
| 物理连接 | 青蓝色实线 | 是 | connectsTo |
| 逻辑承载 | 青绿色虚线 | 当前路径相关时 | runsOn / hostedBy |
| 业务访问 | 带方向粒子的高亮线 | 当前业务路径 | uses / accesses |
| 成员归属 | 空间包围优先；必要时短点线 | 否 | contains |
| 主备关系 | 双线 | 相关对象选中时 | standbyFor |
| 依赖关系 | 细点划线 | 诊断相关时 | dependsOn |
| 故障传播 | 橙红色动态曲线 | 诊断状态 | impacts / propagatesTo |
| 待确认关系 | 灰紫色低透明度虚线 | 是 | unknown |

补充约束：

1. 连线标签默认不常驻，悬停或选中后显示中文语义和内部关系类型。
2. 持续粒子动画只用于当前业务访问、当前故障传播和当前诊断路径。
3. 多条同类关系重合时先聚合为关系束，放大或选中后再拆分。
4. 路径高亮不得改变节点原始布局，只提升相关节点和连线的视觉权重。

### 7.1 跨层映射关系

| 关系类型 | 起点 | 终点 | 触发显示 |
|---|---|---|---|
| `instance_of` | 实例资源 | 对象类型 | 选中实例或查看知识时 |
| `applicable_fault_mode` | 实例/对象类型 | 故障模式 | 候选生成后或用户主动展开 |
| `evidence_mapping` | 实例/观测事实 | 证据规则 | Evidence 创建后 |
| `case_match` | 标准故障现象 | Case 元数据 | Case 路由完成后，仅显示匹配说明 |

跨层关系只表达已有映射，不产生 Candidate、Evidence 或 Conclusion。根因确认前不得用高亮跨层线提前指向最终故障模式。

## 8. 默认展示与规模控制

### 8.1 首次进入

1. 首次进入默认展示“全环境”。
2. 同时展示上层实例拓扑、下层故障知识图谱和少量基线映射。
3. 实例拓扑按“业务→网络→存储”的稳定方向布局。
4. 正常设备默认折叠；知识图谱按语义簇聚合。
5. 无诊断 Session 时不自动展开任何 Case 的异常设备、根因模式或诊断路径。
6. 诊断启动后，只按当前 Session 已知状态逐步展开相关资源和知识节点。

### 8.2 默认展开层级

设备展开后默认展示：

```text
Storage Device
├─ FC/ETH端口聚合
├─ Controller（单体）
├─ Block/NAS Service
├─ LUN/File System（当前路径单体，其余聚合）
├─ Storage Pool
├─ Disk资源簇
└─ BBU/Power/Fan分类聚合
```

### 8.3 节点规模阈值

| 层级 | 建议上限 | 超限处理 |
|---|---:|---|
| 首屏全环境 | 30～50个节点 | 自动聚合非关键资源 |
| 单设备展开 | 不超过80个节点 | 按区域、类型或父资源聚合 |
| 当前诊断对象 | 不聚合 | 强制单体展示 |
| 当前对象上下游一跳 | 原则上不聚合 | 超大邻接时按类型聚合并标数量 |
| 当前业务/影响路径 | 不聚合 | 强制保留完整路径 |

不提供无约束的“一键全部展开”。如确需全量查看，应进入资源清单或专用子视图。

### 8.4 多设备规则

1. 多设备场景默认按设备折叠展示。
2. 只自动展开异常设备、当前选中设备或当前路径设备。
3. 同一时刻建议最多完整展开一台设备；用户主动展开第二台时，第一台可保持半展开。
4. 跨设备复制、冗余或双活关系使用跨容器双线。
5. 集群边界、设备边界、设备内部组件必须保持三级视觉层次。

## 9. 交互规则

### 9.1 节点交互

| 操作 | 行为 |
|---|---|
| 悬停 | 高亮节点描边，显示直接关系和轻量提示 |
| 单击 | 选中节点，打开右侧详情，突出上下游一跳 |
| 双击/展开按钮 | 展开聚合节点或容器 |
| 再次双击/收起按钮 | 收起子资源，保留异常摘要 |
| 右键/更多操作 | 定位上下游、仅看此路径、进入诊断、查看性能/告警 |
| 空白处单击 | 取消选中，恢复当前视图上下文 |

### 9.2 路径交互

“仅看此路径”执行：

```text
保留路径节点和关系
→ 保留主备/冗余路径
→ 保留根因及受影响对象
→ 其他对象透明度降至20%～30%
```

路径模式退出后恢复进入路径模式前的展开状态和视口位置。

### 9.3 视图切换

| 模式 | 强化内容 | 弱化内容 |
|---|---|---|
| 全环境 | 业务、网络、设备整体关系 | 设备内部细节 |
| 设备外部 | 业务、主机、网络和外部依赖 | 设备内部资源 |
| 设备内部 | 设备内部区域及资源关系 | 外部资源 |
| 端到端路径 | 当前业务访问路径、冗余路径 | 非路径资源 |

### 9.4 时间交互

1. 时间范围变化时，布局原则上保持稳定。
2. 资源增删用渐入、渐出表达，不瞬时重排整个画布。
3. 状态变化使用外环和光晕过渡。
4. 用户可回到“当前时间”，恢复实时状态。

## 10. 状态表达与优先级

### 10.1 状态维度

| 状态维度 | 视觉载体 |
|---|---|
| 资源身份 | 节点基础造型和基础色 |
| 健康状态 | 内层状态环/光晕 |
| 诊断角色 | 外层诊断环 |
| 当前选中 | 最外层白色或高对比描边 |
| 路径角色 | 关联线高亮与轻量底光 |
| 非相关对象 | 透明度降低 |

### 10.2 状态优先级

同一节点同时具备多种状态时，按以下层次叠加，不相互覆盖：

```text
节点基础造型
→ 健康状态内环
→ 诊断角色外环
→ 当前选中最外描边
→ 路径高亮
```

诊断角色优先级：

```text
已确认根因 > 根因候选 > 直接受影响 > 间接受影响 > 路径相关 > 普通
```

### 10.3 状态规则

| 状态 | 建议表达 |
|---|---|
| 正常 | 无额外强光，仅保留基础描边 |
| 注意 | 黄色细状态环 |
| 异常 | 橙红色状态环和低频呼吸光 |
| 已确认根因 | 红橙双环，中心或标记强化 |
| 根因候选 | 橙色外环，可显示候选序号/诊断支持分 |
| 受影响 | 黄色外环或影响徽标 |
| 已选中 | 高对比最外描边，不能覆盖异常状态 |
| 冗余有效 | 青绿色稳定路径 |
| 已排除 | 灰色、低透明度，但保留可追溯入口 |
| 数据待确认 | 灰紫色虚线描边 |

## 11. 故障诊断自动聚焦规则

进入诊断上下文后，系统按当前事件已经证明的信息自动聚焦：

```text
定位用户输入对应的业务对象
→ 展开当前已发现的异常范围
→ 展开当前候选对象
→ 展开对象上下游一跳
→ 高亮业务影响路径
→ 保留主备/冗余路径
→ 其余资源降暗
```

自动聚焦约束：

1. 不改变资源的基础空间归属。
2. 不隐藏当前根因、候选根因、直接影响对象和有效冗余路径。
3. 自动聚焦后允许用户手动展开其他资源。
4. 用户操作应被保留，刷新诊断结果时不得无条件重置视口。
5. 根因发生变化时，以过渡动画切换高亮，不整体重排。

## 12. 基线场景呈现规格

### 12.1 场景定义

主机集群通过双 SAN Fabric 访问 Storage-01。Controller-0A 发生热复位，Block Service 切换至 Controller-0B，LUN-DB01 的业务性能短时下降。

### 12.2 必须展示的对象

| 空间 | 对象 |
|---|---|
| 设备外部 | 数据库业务、DB-Host集群、SAN Fabric A/B |
| 设备边界 | Storage-01、FC端口聚合 |
| 控制与服务 | Controller-0A、Controller-0B、Block Service |
| 逻辑资源 | LUN-DB01、Storage Pool-01 |
| 物理资源 | SSD磁盘组、基础设施聚合 |

### 12.3 必须表达的状态

1. 初始模型只显示数据库业务及资源基线，不标记 Controller-0A 为根因。
2. 业务现象事件出现后，数据库业务显示“访问变慢”，相关业务路径进入待验证状态。
3. 候选生成后，Controller、FC/SAN、存储池等候选对象按当前支持分显示候选环。
4. 只有告警、日志和 KPI 事实被转换为证据后，Controller-0A 才逐步升级为领先候选。
5. 接管事实被发现后，Controller-0B 路径才显示冗余接管有效。
6. 根因确认后，Storage-01 边框表达“整机受影响”，但不将所有内部资源标为异常。
7. SSD磁盘组及无关基础设施保持正常并适当降暗。

### 12.4 预期阅读结论

在 `ROOT_CAUSE_CONFIRMED` 之后，用户无需打开详情面板，应能从主画布快速得出：

```text
根因：Controller-0A 热复位
影响：Block Service、LUN-DB01及数据库业务性能
冗余：Controller-0B已接管，业务未完全中断
排除：存储池、磁盘和基础设施当前无明显异常
```

## 13. 右侧详情面板

选中节点后，右侧面板至少包含：

| 分区 | 内容 |
|---|---|
| 基本信息 | 名称、类型、对象ID、所属设备、状态 |
| 诊断信息 | 诊断角色、诊断支持分、影响级别、证据摘要 |
| 告警 | 当前及时间窗口内相关告警 |
| 性能 | 关键指标、异常时间段、趋势入口 |
| 关系 | 上游、下游、主备、依赖、承载关系 |
| 操作 | 仅看此路径、展开上下游、进入诊断、查看知识 |

节点悬浮提示只显示名称、类型、状态和关键数量，不复制完整详情。

## 14. 图例规格

图例分为四组，默认展示摘要，按需展开。

| 图例组 | 内容 |
|---|---|
| 空间归属 | 设备外部节点、集群容器、设备容器、设备内部节点、待确认区域 |
| 资源类型 | 业务、主机、网络、端口、控制器、服务、逻辑资源、物理资源 |
| 关系类型 | 物理连接、逻辑承载、业务访问、主备关系、依赖、故障传播 |
| 状态类型 | 正常、注意、异常、根因、候选、受影响、选中、待确认 |

设备内外的区分必须以空间包围为主，不能只依赖颜色和图例。

## 15. 数据接口最低要求

前端不得自行猜测空间归属和关系类型。每个资源至少需要：

```text
resource_id
resource_type
display_name
health_status
parent_resource_id
storage_device_id
cluster_id（可选）
spatial_domain
internal_zone（设备内部资源必填）
aggregation_key（可选）
```

每条关系至少需要：

```text
source_id
target_id
relation_type
direction
mapping_confidence/status（仅表示关系数据质量，不表示根因概率）
valid_time_range（可选）
```

诊断上下文至少需要：

```text
diagnosis_role
candidate_rank/support_score（可选）
impact_level
path_ids
evidence_summary（可选）
```

`spatial_domain`、`internal_zone` 和 `relation_type` 应采用受控枚举，由资源模型或后端映射层提供。

## 16. 验收标准

### 16.1 展示正确性

- [ ] 首屏使用 `3d-force-graph` 同场景展示实例拓扑、故障知识图谱和跨层映射。
- [ ] 用户可旋转、缩放、平移、拾取、相机聚焦和复位视角。
- [ ] 五个拓扑空间域、四层知识图谱和跨层映射在 3D 空间中可清晰区分。
- [ ] 设备外部资源均位于存储设备容器外。
- [ ] 设备内部资源均位于对应设备容器内。
- [ ] 外部访问链路均通过设备边界端口。
- [ ] 集群、设备、内部组件层次清晰，无同级误导。
- [ ] 内部资源顺序符合“接入—控制与服务—逻辑—物理”。
- [ ] 资源归属主要通过空间包围表达，无大量冗余 `contains` 连线。

### 16.2 信息规模

- [ ] 首屏节点数量控制在30～50个。
- [ ] 单设备展开后原则上不超过80个节点。
- [ ] 当前诊断对象、上下游一跳和关键路径未被错误聚合。
- [ ] 多设备场景仅自动展开异常、选中或路径相关设备。

### 16.3 状态与诊断

- [ ] 基础颜色不用于表达健康状态。
- [ ] 异常、根因、受影响、选中状态可以同时辨识。
- [ ] 故障路径和有效冗余路径能够同时展示。
- [ ] 无关资源降暗但仍可访问。
- [ ] 数据不完整时进入待确认区域，前端无推测性连接。

### 16.4 交互

- [ ] 聚合节点可逐级展开并可恢复原状态。
- [ ] 选中节点可查看上下游及右侧详情。
- [ ] “仅看此路径”不改变基础布局。
- [ ] 视角和时间切换后视口与用户展开状态尽可能保持。
- [ ] 退出诊断聚焦后可恢复此前浏览上下文。

### 16.5 基线场景

- [ ] 初始模型和诊断早期不泄露 Controller-0A 根因。
- [ ] 只有 `ROOT_CAUSE_CONFIRMED` 之后，用户才可在不打开详情面板的情况下识别 Controller-0A 为根因。
- [ ] 用户可识别 Block Service、LUN-DB01 和数据库业务受到影响。
- [ ] 用户可识别 Controller-0B 已接管且业务未完全中断。
- [ ] 用户可识别存储池、磁盘和基础设施当前无明显异常。

## 附录A：正式规则摘要

1. 实例拓扑与故障知识图谱使用同一个真实 3D 场景，通过受控跨层关系连接。
2. 存储设备采用 3D 容器造型，不与内部资源画成同级普通节点。
3. 设备外资源位于容器外，设备内资源必须位于容器内。
4. FC、ETH等端口位于设备边界，承担内外连接锚点。
5. 设备内部按前端接入、控制与服务、逻辑资源、物理资源分区。
6. 资源归属优先通过空间包围表达，避免大量 `contains` 连线。
7. 存储集群与存储设备采用两级嵌套边界。
8. 设备边框表达整机状态，内部节点独立表达组件状态。
9. 外部链路不得直接穿透到 Controller、LUN、文件系统或存储池。
10. 默认只展开选中对象；诊断启动后再按 Session 逐步展开异常与路径相关资源。
11. 基础布局保持稳定，观察角度和路径高亮只改变显隐与视觉权重。
12. 状态按“健康内环—诊断外环—选中描边”分层叠加。
13. 数据缺失或冲突时进入待确认区域，禁止前端猜测。
