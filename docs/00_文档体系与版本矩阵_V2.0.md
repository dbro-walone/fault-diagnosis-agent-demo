## 3. 统一枚举口径

### CandidateStatus

```text
INITIAL | ACTIVE | LEADING | WEAKENED | CONFLICTING |
CONFIRMED | NOT_CONFIRMED | INSUFFICIENT_EVIDENCE
```

### TaskStatus

```text
PLANNED | READY | RUNNING | SUCCEEDED | FAILED | PARTIAL |
DATA_MISSING | CANCELLED | SKIPPED
```

旧 Skill `SUCCESS` 映射为 `SUCCEEDED`，`EMPTY` 映射为 `DATA_MISSING`；若查询完整且明确返回 0 个匹配，Adapter 可另外生成 `absence` Fact，但状态仍不能等同“对象正常”。

### EvidenceEffect

```text
STRONG_SUPPORT | SUPPORT | WEAKEN | CONFLICT | NEUTRAL
```

旧 `stance=support` 根据强度映射为 `SUPPORT/STRONG_SUPPORT`；`contradict` 映射为 `WEAKEN`，只有事实与候选核心断言直接矛盾时才映射 `CONFLICT`。

### RuntimeMode

```text
LIVE | PAUSED | REPLAY
```

## 5. 不修改项

- Case V1.0 的文件目录、ID、原始观测和时间字段不改；
- `validate_case_package.py` 继续只校验 Case V1.0；
- Planner 负责选择下一验证目标，不负责根因裁决；
- Skill 负责返回事实，不输出 Evidence 和诊断支持分；
- 前端只负责投影，不进行候选计算和证据推理。

## 6. 开发实施顺序

1. 先实现 Runtime Snapshot、Event Reducer、Adapter 和回放；
2. 再实现 Projection Store、聚合钻取和 LUI View Model；
3. 接入确定性 Case Planner 与 Mock Skill Executor；
4. 完成三类 Case 回归；
5. 最后替换为真实 Skill 或大模型 Planner，保持契约不变。
