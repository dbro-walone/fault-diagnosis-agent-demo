# 故障诊断 Agent 推理模块与候选更新规则基线 V1.0

> 总纲边界：推理模块只在故障现象完成标准化、Case 路由成功并创建 `diagnosis_session` 后运行。3D 实例拓扑和故障知识图谱为候选生成与证据解释提供模型依据，但推理结果必须通过统一 Runtime Event 写入 Session；推理模块不直接操作 3D 场景或前端组件。

## 1. 文档定位

本规范用于故障诊断 Agent 可视化原型，定义候选根因、诊断证据、候选更新、Planner 重规划和诊断结束的演示规则。

V1 采用：

> Case Mock 驱动的候选假设推理 + 证据增减分 + 最小证据链确认 + 状态机控制

目标是准确展示“为什么怀疑、如何取证、候选为何变化、为什么重规划以及最终为何确认或不能确认”，不将当前规则包装为生产级概率模型或通用诊断算法。

## 2. V1 能力边界

V1 保证：

- 候选具体到“对象 + 故障模式”；
- 展示证据对候选的支持、削弱或中性作用；
- 展示候选诊断支持分、状态和排序变化；
- 依据统一条件触发 Planner 重规划；
- 依据最小证据链和竞争候选检查确认根因；
- 正确处理冲突、并列候选和证据不足。

V1 暂不实现：

- 基于真实数据训练或校准的概率模型；
- 通用证据权重学习；
- 真实大模型自由生成候选和推理路径；
- 生产级知识图谱推理、因果发现和不确定性计算；
- 跨 Case 通用的自动阈值优化。

候选、证据关系、分值变化和最小证据链均可由 Case 的预期事件轨迹预设，推理模块按统一协议产生或解释事件。

## 3. 候选根因生成

### 3.1 候选来源

候选可由三类输入生成：

| 来源 | 作用 |
|---|---|
| 故障知识与机理关系 | 根据故障现象生成可能原因 |
| 资源与拓扑 | 将抽象原因定位到具体对象 |
| 新发现的异常事实 | 新增或细化候选故障模式 |

模型探索态中可浏览完整的聚合知识结构，但当前 Case 的候选只能依据 Agent 当时可见的输入、拓扑范围和知识规则生成。不得读取 `conclusion.json`、未来事件或尚未执行 Skill 的结果来生成答案级候选。

### 3.2 候选结构

```yaml
candidate:
  id: candidate_01
  object: Controller-0A
  fault_mode: 控制器异常或发生复位
  generated_from:
    - 业务访问时延升高
    - I/O路径经过Controller-0A
    - 控制器中断可造成路径切换
  support_score: 30
  status: ACTIVE
```

### 3.3 生成规则

1. 候选必须具体到“对象 + 故障模式”；
2. 候选只是待验证假设，不是事实；
3. 初始候选建议控制在 3～5 个；
4. 新证据可新增、细化或合并候选；
5. V1 候选清单可以由 Case 预设。

控制器热复位 Case 的初始候选示例：

1. `Controller-0A 控制器异常或复位`
2. `前端 FC 链路异常`
3. `存储池性能过载`
4. `后端磁盘异常`

## 4. 证据及其候选作用

### 4.1 证据最小结构

```yaml
evidence:
  id: evidence_05
  source_execution_id: exec_003
  fact: Controller-0A在14:32:17发生热复位
  candidate_id: candidate_01
  effect: STRONG_SUPPORT
  reason: 热复位可直接造成主I/O路径短时中断
```

### 4.2 证据作用

| 作用 | 默认分值 | 含义 |
|---|---:|---|
| `STRONG_SUPPORT` | +30 | 直接故障事件或关键机制证据 |
| `SUPPORT` | +15 | 对象、时间、现象或影响表现一致 |
| `WEAKEN` | -15 | 关键预期异常未出现，候选合理性下降 |
| `NEUTRAL` | 0 | 当前事实不能区分候选 |

以上分值是演示默认值，Case 可以覆盖。

### 4.3 证据有效性检查

证据影响候选前至少检查：

1. **对象相关性**：证据是否位于候选对象或直接关联对象；
2. **时间相关性**：证据是否处于故障窗口或合理传播窗口；
3. **机理相关性**：证据能否解释当前故障现象。

同一事实可以影响多个候选，但必须分别说明影响方向和原因。

## 5. 诊断支持分

### 5.1 定义

候选分数统一称为“诊断支持分”：

> 表示当前证据对候选根因的相对支持程度，用于候选排序和过程展示，不代表故障概率或统计置信度。

禁止将 `86` 展示为“86% 根因概率”或“86% 置信度”。

### 5.2 默认规则

| 参数 | V1 默认值 | 说明 |
|---|---:|---|
| 分数范围 | 0～100 | 超出范围时截断 |
| 初始候选分 | 20～35 | Case 根据先验相关性预设 |
| 领先候选参考分 | ≥60 | 只用于排序和展示 |
| 根因确认参考门槛 | ≥80 | 不能单独触发根因确认 |

分数更新公式：

```text
新诊断支持分 = clamp(旧诊断支持分 + 证据作用分, 0, 100)
```

分数只用于相对排序。多个弱证据累计达到门槛，仍不能替代直接故障或关键机制证据。

## 6. 候选状态

| 状态 | 含义 |
|---|---|
| `INITIAL` | 已生成，尚未验证 |
| `ACTIVE` | 正在取证 |
| `LEADING` | 当前领先候选 |
| `WEAKENED` | 被证据明显削弱 |
| `CONFLICTING` | 存在未消解的关键冲突 |
| `CONFIRMED` | 满足根因确认条件 |
| `NOT_CONFIRMED` | 当前未形成可确认结论 |

不轻易使用 `EXCLUDED`。除非存在明确矛盾事实，否则只表示候选被削弱或当前证据不支持。

## 7. Planner 重规划触发

并非每次分数变化都触发重规划。满足以下任一条件时可以触发：

| 触发条件 | 典型动作 |
|---|---|
| 出现新的强支持证据 | 转向验证触发机制和影响链 |
| 新增或细化候选 | 增加对应验证任务 |
| 原领先候选被明显削弱 | 暂停后续任务并提升其他候选 |
| 候选排序发生关键变化 | 调整 Skill 查询顺序 |
| 出现关键证据冲突 | 增加冲突消解任务 |
| 候选接近根因确认 | 增加反证和竞争候选检查 |
| 当前任务无法继续 | 查询替代数据或结束为证据不足 |

```yaml
replan_trigger:
  type: STRONG_EVIDENCE_FOUND
  evidence_id: evidence_05
  reason: 发现控制器热复位直接故障证据
  affected_candidates:
    - candidate_01
```

## 8. 最小证据链

### 8.1 统一模板

不同 Case 使用相同结构表达最小证据链，具体内容由 Case 配置：

| 证据环节 | 作用 | 是否必需 |
|---|---|---:|
| 故障事实或关键机制 | 证明候选对象发生相关异常 | 是 |
| 对象与影响路径 | 证明故障对象位于业务路径或传播链 | 是 |
| 时间一致性 | 证明故障与业务异常时间匹配 | 是 |
| 影响表现 | 证明故障能够解释主要业务现象 | 是 |
| 竞争候选检查 | 防止仅因单一强证据过早确认 | 是 |
| 辅助参考 | 相似案例、历史经验等 | 否 |

相似案例只能作为辅助证据，不能单独确认根因。

### 8.2 控制器热复位 Case 示例

```text
直接事件：Controller-0A发生热复位
    ↓
触发机制：复位前出现watchdog_timeout日志指纹
    ↓
影响传播：0A主I/O中断，0B发生接管和吞吐切换
    ↓
业务表现：LUN时延在同一窗口显著升高
    ↓
竞争检查：FC链路无掉线、CRC无异常增长
```

## 9. 关键竞争候选检查

“关键竞争候选已检查”采用以下 V1 基线：

1. 至少识别一个能够解释主要现象的关键竞争候选；
2. 至少执行一项具有区分性的验证任务；
3. 验证结果已返回，不得以 `FAILED` 作为完成；
4. 结果应削弱竞争候选，或说明其不能解释关键对象、时间或影响链；
5. 若结果为 `EMPTY` 或 `PARTIAL`，必须结合查询覆盖范围判断，不能自动视为排除；
6. 仍存在未检查且足以改变结论的竞争候选时，不得确认根因。

V1 不要求检查全部低优先级候选。是否属于“关键竞争候选”由 Case 配置预设。

## 10. 根因确认规则

候选达到 `CONFIRMED` 必须同时满足：

```text
诊断支持分达到参考门槛
+ 存在直接故障或关键机制证据
+ 故障对象位于影响路径
+ 时间与业务异常一致
+ 能解释主要故障现象
+ 已完成关键竞争候选检查
+ 不存在未解决的关键冲突
= ROOT_CAUSE_CONFIRMED
```

分数达到门槛但证据链不完整时，必须继续取证或输出不能确认。

## 11. 特殊情况

### 11.1 证据冲突

存在影响根因成立的关键冲突时：

1. 候选状态更新为 `CONFLICTING`；
2. Planner 生成时间对齐、对象核对、影响验证等冲突消解任务；
3. 冲突未解释前不得确认根因；
4. 无法消解时输出冲突说明和缺失信息。

正负分相抵不能替代冲突消解。

### 11.2 并列候选

当领先候选分差小于 10，且均缺少决定性证据时，输出：

```text
PROBABLE_CAUSES
```

同时列出：

- 各候选已有的主要证据；
- 各候选缺少的决定性证据；
- 下一项最有区分度的验证任务。

不得通过人为增加少量分数强行选择唯一根因。

### 11.3 证据不足

以下情况输出：

```text
INSUFFICIENT_EVIDENCE
```

- 关键 Skill 失败或数据缺失；
- 只有业务现象，没有具体故障事实；
- 只有相似案例，没有本次故障证据；
- 所有候选均未形成最小证据链；
- 关键时间窗口或对象无法确定；
- 当前查询预算或演示流程已经结束。

输出必须说明当前可确认内容、不可确认内容、缺失证据和建议补充数据。

## 12. 候选更新流程

每次 Skill 返回后，推理模块按固定顺序执行：

```text
读取Skill事实
→ 判断是否形成有效证据
→ 关联一个或多个候选
→ 判断支持、削弱或中性
→ 更新诊断支持分
→ 更新候选状态与排序
→ 检查证据冲突
→ 检查最小证据链和竞争候选
→ 决定继续、重规划或结束
```

## 13. 推理更新协议

```yaml
reasoning_update:
  evidence_id: evidence_05

  candidate_changes:
    - candidate_id: candidate_01
      effect: STRONG_SUPPORT
      score_before: 32
      score_after: 62
      status_before: ACTIVE
      status_after: LEADING
      reason: 热复位事件与对象、时间和故障机理一致

  chain_progress:
    fault_fact: SATISFIED
    affected_path: SATISFIED
    time_alignment: SATISFIED
    impact_explanation: PENDING
    competitor_check: PENDING

  decision:
    action: REPLAN
    reason: 已发现直接故障证据，需要验证触发机制、影响链和竞争候选
```

`decision.action` 建议保留：

- `CONTINUE`：按当前计划继续；
- `REPLAN`：触发 Planner 重规划；
- `CONFIRM`：确认根因；
- `PROBABLE_CAUSES`：输出多个可能原因；
- `INSUFFICIENT_EVIDENCE`：证据不足并结束。

## 14. V1 冻结原则

1. 候选由知识机理、资源拓扑和新增异常事实共同产生；
2. 候选必须具体到“对象 + 故障模式”，初始控制在 3～5 个；
3. 分数称为“诊断支持分”，不是概率或统计置信度；
4. 分数用于排序和展示，不能单独确认根因；
5. 证据按强支持、支持、削弱和中性影响候选；
6. 根因确认必须满足最小证据链、竞争候选检查和冲突消解；
7. 最小证据链使用统一模板，具体要求由 Case 配置；
8. 关键竞争候选至少完成一项有效、具有区分性的检查；
9. 冲突未解决时不能确认根因；
10. 并列候选输出多个可能原因，关键证据不足时明确结束为证据不足；
11. V1 分值、候选关系和推理路径可由 Case 预期事件预设，Runtime 负责统一推进与回放；
12. 后续真实大模型推理可以替换候选生成和判断层，但应尽量保持事件协议兼容。
